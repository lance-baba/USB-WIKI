## 2. 功能实现说明

### 2.1 运行时引擎与自愈启动器

| 设计约定 | 实现情况 |
| :--- | :--- |
| `python311._pth` 去掉 `import site` 注释 + 追加 `./Lib/site-packages` | `setup_runtime_windows.py :: step2_patch_pth()`，写入 `python311.zip / . / Lib/site-packages / import site` |
| 端口 28765 起探测，占用则 +1 至 28775，超限弹窗报警 | `launcher.probe_port()`，`PORT_ATTEMPTS = 10`，全失败抛错并由 `main()` 打印失败原因后返回码 2 |
| 监听成功后 `webbrowser.open_new_tab` | `launcher._open_browser()`，先做 TCP 可达性探测最多 2s 再唤出 |
| 启动前检测 `-wal` 且 size>0 → `PRAGMA wal_checkpoint(RESTART)` | `db.wal_self_heal()`，在 `launcher.main()` 与 `AppContext.boot()` 两处调用，早于任何业务连接 |
| 前端「安全退出」按钮 → `/api/system/shutdown` | `index.html` 头部按钮 → `server._route_post` → `Server.request_shutdown()` |
| `SetConsoleCtrlHandler` + `signal.SIGINT` | `launcher._install_exit_hooks()`，回调对象以 `_CALLBACK_REF` 持有防 GC |
| 500ms 内 `wal_checkpoint(TRUNCATE)` + 按需 `VACUUM` | `db.checkpoint_and_close()`；实测退出耗时 **210ms**，VACUUM 仅在碎片率 >25% 时触发 |
| 清理 `-wal` / `-shm` | `checkpoint_and_close()` 末尾显式 unlink；实测退出后仅剩 `cache.db` |

### 2.3 存储引擎与双路混合检索

| 设计约定 | 实现情况 |
| :--- | :--- |
| 真相源 `data/notes/`，`cache.db` 可全量重建 | `indexer.rebuild_all()` 清空所有索引表后重扫 |

## 3. 三项隐蔽工程细节

### 细节 #1 · exFAT 同步判定防范「等长编辑漏扫」 ✅
`core/sync.py :: NoteSyncer._decide()` 实现设计建议的三分支，并额外补齐「时间倒流」分支：

| 条件 | 判定依据 | 动作 |
| :--- | :--- | :--- |
| `current_mtime > last_mtime + 2.0s` | `mtime-advanced` | 重建索引（**即使字节数完全相同**） |
| `|Δt| ≤ 2.0s 且 file_size ≠ last_size` | `size-changed` | 重建索引 |
| `|Δt| ≤ 2.0s 且 file_size == last_size` | `same-length-edit` | 比对**前 4KB XXH64/blake2b**，不同则重建 |
| `Δt < -2.0s` | `mtime-rewound` | 保守重建 |
| 基线缺失（首次升级/旧库） | `baseline-missing` | 重建一次以建立哈希基线 |

哈希基线持久化在 `documents.sha1` 字段，重启后由 `seed_from_db()` 回灌，不重复付代价。
测试覆盖：等长编辑真实命中 `same-length-edit`、无变化不误报、时间明显后移 / 大小变化 / 时间倒流三分支各自命中。

### 细节 #2 · Windows 嵌入式环境终端编码锁死 ✅
`启动-Windows.bat` 前三行即：
```bat
chcp 65001 > nul
set PYTHONIOENCODING=utf-8
set PYTHONUTF8=1
```
并且**批处理本体保持纯 ASCII** —— 所有中文提示（banner、错误说明、URL）一律由 Python 以 UTF-8 输出；
`log_util._SafeStreamHandler` 在控制台仍不支持 UTF-8 时以 `errors="replace"` 转义落盘，绝不抛 `UnicodeEncodeError`。
测试断言：三个环境变量齐备、编码设置在调用 Python 之前、文件内无任何非 ASCII 字符。

### 细节 #3 · `onnxruntime` 老旧宿主机 AVX2 崩溃 ✅
`core/embedder.py` 三层防护：
1. **CPU 特性位预检** —— Windows `IsProcessorFeaturePresent`（PF_SSE4_2 / PF_AVX / PF_AVX2）、Linux `/proc/cpuinfo`、macOS `sysctl`；若 SSE4.2 与 AVX2 均缺失直接否决，不进入导入。
2. **子进程 import 探针** —— `probe_onnxruntime()` 在独立进程中 `import onnxruntime`；命中 SIGILL（返回码 -4 / 3221225477）时只牺牲子进程，系统拿到负结果。结果带 7 天磁盘缓存（`runtime/.onnx_probe.json`），避免每次冷启动付子进程开销。
3. **顶层 `except BaseException`** —— `OnnxEmbedder._lazy()` 兜住任何未预期异常。

一旦判定不可用，`embedder.resolve()` 自动沿 `local_onnx → ollama → api → local_hash` 逐级降级，
并把「检测到 CPU 指令集不兼容本地嵌入引擎，已自动切换」推入控制台运行详情。
测试断言：探针不抛异常、CPU 特性结构完整、哈希兜底确定性与区分度达标。

## 4. 已修复的真实缺陷（含根因）

| # | 缺陷 | 影响 | 修复 |
| :-: | :--- | :--- | :--- |
| 1 | `sqlite-vec` 仅在首个连接加载 | 多线程下报 `no such module: vec0`，**向量写入全部失败** | 改为**每连接**调用 `_try_load_vec()`；`sqlite_vec` 模块对象进程内缓存 |
| 2 | `vec0` 不支持 `INSERT OR REPLACE` | 重复索引同一文档时 `UNIQUE constraint failed on chunks_vec primary key` | `purge_document` 以 **vec 表真实内容前缀扫描**保证清除彻底；写入侧再加「先删后插」自愈 |
| 3 | FTS5 `INSERT OR REPLACE` 静默追加重复行 | 重复行污染 bm25 排序，同一 chunk 多次占据候选位 | 改为事务内**显式 `DELETE` 后 `INSERT`** |
| 4 | Windows `SO_REUSEADDR` 使端口探测失效 | 端口避让逻辑形同虚设，甚至可能**抢占其它进程端口** | `probe_port` 不设该选项；`Server.allow_reuse_address = (os.name != "nt")` |
| 5 | `net_util.http_get` 未捕获 `URLError` | Ollama 未启动时异常冒泡，探针线程崩溃、降级判定失真 | 统一折算为 `status=0`，绝不向上抛异常 |
| 6 | 批处理括号块内 `%ERRORLEVEL%` + `goto :end` | 解析期展开导致捕获过期退出码；`py` 失败即跳过 `python` 候选 | 改为 label/goto 扁平结构，候选逐个尝试 |
| 7 | `ollama_status` 把 3 元组当 2 元组解包 | 探针线程抛 `ValueError`，健康状态永远显示「未探测」 | 修正解包；全局排查同类调用点 |
| 8 | **向量表维度沿用 `config.embedding_dim`，未跟随自动探测结果** | 用 Ollama `nomic-embed-text`（768 维）时，vec 表仍按 512 建，**768 维向量全部被拒写** → 向量路 0 候选且无报错 | `context.boot` 调整顺序：先解析嵌入源拿到真实维度，再 `init_schema()` |
| 9 | **中文长问句整句当一个短语做 trigram 匹配** | 「位置编码有什么用」因笔记里没有这句连续子串而 **0 命中**（且静默） | `_fts_terms` 对中文长串切滑动 3-gram + 保留原串加权，OR 语义召回 |
| 10 | Ollama 配置的嵌入模型不存在时**静默失败** | 只在逐文档索引时报"向量化失败"，用户不知道该改哪 | 启动即比对 `/api/tags`，明确告警「未安装模型 X，可 pull 或改用已装的 …」 |
| 11 | **兜底嵌入源覆盖主源签名，形成「降级→重建」破坏性循环** | Ollama 一关就降级到 512 维哈希并覆写签名，开回 Ollama 又被要求重建，来回折腾会反复清空索引 | 兜底时**整体关闭向量路**（回归「降级至纯 FTS5」的原始设计），绝不触碰已有索引与签名 |
| 12 | **测试套件会删光用户真实知识库** ⚠ | `reset_workspace()` 清 `data/notes/*.md`；加"跑完自清理"后，跑一次测试即删除用户全部笔记 | 数据根目录重定向到临时目录（`paths` 全为属性访问，运行时替换即全局生效），并新增「真实知识库未被测试改动」断言做安全红线复核 |
| 13 | **XLSX 工作表名映射失败 + 首行未作表头** | 路径未归一化导致 `sheet_names` 查不到（全显示 `sheet1`）；表格表头被写成「列1/列2」而真实表头降级为数据行 | rels 的 Target 统一归一化为 `xl/...` 再比对；首行非空即作为 Markdown 表头 |
| 14 | 多格式导入的**标题取自元数据还是文件名** | 合成素材时复用同一份 `dc:title` 导致三个文件标题串号——暴露了「元数据优先」这一策略需要显式测试覆盖 | 明确策略：优先 `docProps/core.xml` 的 `dc:title`，缺失则回退文件名；两条路径均加入测试断言 |
| 15 | **PDF 抽取丢失段落结构** | `pypdf` 把整页文字连成一片，没有段落空行 → Parent-Child 切片无法按段断开，长文档会出现超 800 字的父块并在句子中间硬切 | 改用 `pdfminer.six` 作为主力后端（保留段间距）；`pypdf` 降为后备。实测同一长文档：pdfminer 最长父块 **704 字**（符合 800 目标），pypdf **808 字**（超限硬切） |
| 16 | **自愈过程信息被当成告警弹给用户** ⚠ | 界面顶部四个状态全绿（系统完全正常），下方却挂着「onnxruntime 不可用: FAIL ModuleNotFoundError…」和「向量维度已自动适配 512→768」两条黄条。前者夹带原始异常串，后者其实是好消息——用户被误导以为出了问题 | 告警**按「是否需要用户行动」分级**：`warnings`（能力缺失/配置错误，上告警条）与 `notes`（系统已自愈的过程信息，进「设置 → 运行详情」）。同时把 ONNX 失败原因**人话化**：`onnxruntime 不可用: FAIL ModuleNotFoundError No module named 'onnxruntime'` → `本地 ONNX 嵌入引擎不可用（未安装 onnxruntime），已按降级链继续` |
| 17 | **剪藏页第三张卡片布局塌陷** | `body` 是 `overflow:hidden` 而剪藏面板没有滚动容器；`.card` 自带 `min-height:0`，3 张卡片在受限列向 flex 中被压缩 → 「粘贴文字入库」的 textarea 高度塌成 0，卡片内容被裁掉，「保存并索引」按钮错位 | 面板改为 `overflow-y:auto`，卡片 `flex:0 0 auto` 保持自然高度；移除会覆盖 CSS 的内联 `flex:1`，textarea 用 `min-height:220px` 固定 |

| 18 | **中文文件名导致 HTTP 响应头编码崩溃** ⚠ | `Content-Disposition: ... filename="{file.name}"` 把中文文件名直接塞进 header，而 HTTP 头**只能是 latin-1** → `UnicodeEncodeError`。更糟的是异常发生在 `send_response` 之后，响应头已部分发出，兜底逻辑又试图补发一个 JSON 错误响应 → **协议错乱，客户端一直等到超时（表现为「接口挂死」）** | ① 按 **RFC 6266** 双字段编码：`filename="<ASCII 回退名>"; filename*=UTF-8''<百分号编码真名>`；纯中文名回退为 `download.<ext>` 而非退化成 `.pdf` 这种隐藏文件名。② 新增 `_fail()` 统一异常出口：**响应头已发出时只记日志并断开连接**，不再补发响应 |
| 19 | ONNX 模型文件名被误改 | 一次编辑中 `bge-small-zh-q4.onnx` 被写成 `bge-small-q4.onnx`，会导致本地嵌入模型永远找不到 | 立即修正并加断言校验（`paths.ONNX_MODEL_FILE.name`） |

| 20 | **抓取网页整页乱码（编码默认值陷阱）** ⚠ | 响应头 `Content-Type: text/html`
不带 `charset` 时，requests 按 RFC 2616 默认成 `ISO-8859-1`；而原写法
`resp.encoding or resp.apparent_encoding` 中 `ISO-8859-1` 是真值，`or` 直接短路，
内容嗅探永远取不到。实测 docs.python.org：Markdown 笔记 92 处、原件 HTML 116 处乱码 |
新增 `resolve_html_encoding()`：HTTP 头 charset → BOM → `<meta charset>` → 字节嗅探，
并先验证自述 charset 真能解开（防页面说谎）。urllib 回退路径同时修复（原来硬编码 utf-8，
且丢弃了响应头）。同页实测：两个产物均 0 处乱码 |
| 21 | **删除笔记后原件不回收** | 删除路径只清理孤儿切片，没管 `data/originals/`；
反复剪藏再删笔记后堆了 28 份孤儿原件共 **13.48 MB**（单份剪藏 HTML 就 1 MB），
在 U 盘上无声增长 | 新增 `purge_orphan_originals()` 并接入同步周期；
带安全阀：笔记数为 0 却存在原件时判定为目录异常、拒绝删除 |
| 22 | **原件回收口径不一致导致全部误删**（自查发现）| 函数原签名收 `active_stems`，
但调用方传的是 `disk.keys()`（`notes/x.md` 形式），两边口径不一致 → 永不匹配 → 全删 |
改为**收笔记路径、内部自行推导 stem**，从签名上杜绝调用方口径错误；
回归测试刻意传相对路径以锁住该场景 |

## 5. 多格式转换：为什么不上 OmniParse

`OmniParse` 的思路（万物统一成 Markdown 再建索引）是对的，但它的实现依赖 Surya OCR / Whisper / marker
等**模型**，容器镜像 GB 级、需要 GPU，与本项目「U 盘便携、零安装、发布包 122MB」的定位直接冲突。

**因此采用同等思路的轻量化落地，并严格区分「需要模型」与「不需要模型」两件事：**

| 格式族 | 是否需模型 | 实现 | 体积代价 |
| :--- | :--- | :--- | :--- |
| `.docx` / `.pptx` / `.xlsx` | ❌ 不需要 | OOXML 本质是 **ZIP + XML**，用标准库 `zipfile` + `xml.etree` 直接解出层级与表格 | **0** |
| `.epub` | ❌ 不需要 | 同上（解 container.xml → OPF → spine 顺序） | **0** |
| `.html` / `.mhtml` / `.eml` | ❌ 不需要 | 复用已有 trafilatura | **0** |
| `.csv` / `.json` / `.yaml` / `.xml` / 代码 / 字幕 / RTF | ❌ 不需要 | 标准库 | **0** |
| `.pdf` | ❌ 不需要（文本型） | `pdfminer.six`（主用，自带 149 个东亚 CMap）+ `pypdf`（后备） | **+26MB**（96→122MB） |
| 扫描件 PDF / 图片 / 音视频 | ✅ **需要** OCR/ASR | **明确不做**，给出可操作提示 | — |

**结论：20+ 种格式的覆盖只多花了 4MB。** 真正的分界线不是「格式多不多」，而是「要不要模型」。

> 若未来确实需要 OCR / 音视频转写，正确做法是**外挂**（调用本地 Ollama 或云端 API），
> 而不是把模型打进发布包 —— 这样便携包的体积与零安装承诺都不会被破坏。

## 6. 已知限制

1. **体积显著超出最初规划**
   规划阶段按直接依赖估算，未把传递依赖树算进去 —— 实际落地后翻了一倍。
   逐项构成（均为运行必需，已逐项验证）：

   | 组件 | 体积 | 说明 |
   | :--- | ---: | :--- |
   | Python 3.11 embeddable 本体 | ~21 MB | python311.dll / .zip / libcrypto / sqlite3.dll 等 |
   | `babel` | 32 MB | **`courlan` 在 import 期硬依赖 `babel.Locale`** → 而 courlan 是 trafilatura 的依赖链上游；实机验证「删掉即 `ModuleNotFoundError`」，不可移除 |
   | `pip`（含 setuptools 已剔） | 13 MB | 保留以便在 U 盘上追加包，可维护性优先 |
   | `pdfminer.six` | 9.4 MB | PDF 主力后端。其中 **7.9MB 是 149 个东亚 CMap 映射表** —— 中文 PDF 能正确抽出汉字正靠它 |
   | `cryptography` + `cffi` + `pycparser` | 12.5 MB | pdfminer.six 的**硬性 import 依赖**（实测移除即 `ModuleNotFoundError`，不可裁剪）；仅加密 PDF 才会真正用到 |
   | `pypdf` | 4 MB | PDF 后备后端（轻量、零编译依赖） |
   | `lxml` | 9.3 MB | 正文解析加速（全系统唯一 C 扩展） |
   | dateparser / justext / pytz / regex / tzdata / 其余 | ~21 MB | trafilatura 抽取链传递依赖 |

   已剔除项：`onnxruntime`(≈120MB) + `numpy`(27MB) + `setuptools`(6.5MB) + protobuf/flatbuffers 残留 + `__pycache__`。
   **ONNX 嵌入引擎改为按需安装**（`--with-onnx`），因为缺少模型文件时 onnxruntime 不提供任何能力，
   却会让发布包膨胀一倍以上。

2. **TC-02（写入过程中物理拔盘）需人工验证**
   必须在真实 exFAT 格式 USB 2.0/3.0 介质上人工执行。代码侧已具备对应保障
   （`synchronous=NORMAL` 抑制写放大、启动 WAL 自愈、写操作上下文管理器 + 失败即抛不重试），但**未经物理介质实测**，属发布前必须补齐的硬门槛。

3. **本地 ONNX 嵌入模型未随包分发**
   `setup_runtime_windows.py --with-onnx` 可一并安装 onnxruntime 并下载 `bge-small-zh-v1.5` 量化 ONNX；
   未启用时按降级链表落到 Ollama / API / `local_hash`，控制台会明示告警。
   另：`OnnxEmbedder` 的 tokenizer 目前为字符级近似编码，接入真实 `tokenizer.json`（WordPiece）后语义精度会显著提升 —— 属**建议的后续增强**。

4. **macOS Gatekeeper 首次启动引导**
   `启动-macOS.command` 内置 `xattr -d com.apple.quarantine` 自解隔离；若用户从压缩包解出后仍被拦截，
   需手动「右键 → 打开」。正式封版前建议补充图文引导。

5. **`auto` 模式在无 Ollama 且无 API Key 时返回离线检索摘要**
   这是 设计上明确要求的「永不崩溃」兜底行为，但答案质量弱于 LLM 生成；
   控制台会在 `meta` 帧与告警栏中明确标注「当前为纯离线 FTS5 检索模式」。

## 三、Schema Version 逻辑：**存在实质缺陷（P0）**

`app/core/db.py`：

```python
META_SCHEMA_VERSION = "schema_version"
SCHEMA_VERSION = "1.3"

# init_schema() 内（第 238-241 行）
c.execute(
    "INSERT OR REPLACE INTO sys_meta(key, value) VALUES(?, ?)",
    (META_SCHEMA_VERSION, SCHEMA_VERSION),
)
```

### 问题 S-1：版本号每次连接都被覆盖，导致永远无法判断旧库版本

`INSERT OR REPLACE` 会在**每次** `init_schema()` 时把库内版本改写为当前版本。
于是：

- 打开一个 1.2 的旧库 → 立即被写成 1.3 → **1.2 这个事实被抹掉**
- 后续任何时刻都无法回答「这个库原来是什么版本建的」
- 结构变更（如新增 `doc_meta`）后旧库不会补齐，用户也不会收到任何提示

### 问题 S-2：`SCHEMA_VERSION` 只写不读
全仓库检索该常量，**没有任何一处与库内记录值做比对**。它当前只是一个被写进去的字符串，
不构成任何护栏。

### 问题 S-3：无升级机制
不存在 migration / rebuild 分支。三种情况（全新库 / 版本一致 / 版本偏旧）行为相同，
一律静默覆盖。**这是本轮最高优先级。**

## 四、CI：Windows 实质未完成测试（P0）

### 实测（最新一次运行 `34965102453`，分支 main）

```
windows-latest / Python 3.13 → failure
   ✅ 安装依赖   ❌ 环境自检   ⏭ 运行测试套件   ⏭ 启动冒烟
windows-latest / Python 3.11 → failure
   ✅ 安装依赖   ❌ 环境自检   ⏭ 运行测试套件   ⏭ 启动冒烟
ubuntu-latest  / Python 3.13 → success（全步骤 ✅）
ubuntu-latest  / Python 3.11 → success（全步骤 ✅）
```

### 问题 C-1：`continue-on-error` 掩盖了上述失败
`.github/workflows/tests.yml:22`

```yaml
continue-on-error: ${{ matrix.os == 'windows-latest' }}
```

因此**工作流整体显示 success**（GitHub Actions 列表页 5 条记录全绿），
而 Windows 上**测试套件与冒烟测试从未执行**。这是典型的「表面绿、实际没测」。

### 问题 C-2：根因（已做机制复现，非推测）

失败的「环境自检」步骤用内联 heredoc 打印中文，**未设置编码环境变量**：

```yaml
- name: 环境自检
  shell: bash
  run: |
    python - <<'PY'
    ...
    print(f"  onnxruntime  {'存在（非预期）' if onnx else '缺失（预期：用于验证降级链）'}")
    PY
```

而**同一个文件中的「启动冒烟」步骤**显式设置了，注释还写着原因：

```yaml
- name: 启动冒烟
  env:
    PYTHONUTF8: "1"          # 内联脚本不导入应用模块，需自行保证输出编码
    PYTHONIOENCODING: utf-8
```

**机制复现**（本机）：

```
$ PYTHONIOENCODING=cp1252 python -c "print('存在（非预期）')"
Traceback (most recent call last):
  File "encodings\cp1252.py", line 19, in encode      ← UnicodeEncodeError

$ PYTHONUTF8=1 PYTHONIOENCODING=utf-8 python -c "print('存在（非预期）')"
存在（非预期）                                          ← 正常
```

GitHub 的 `windows-latest` runner 是**英文 locale（cp1252）**，无法编码中文；
本地是 cp936 所以复现不出。**作者知道这条规则并写进了注释，只是漏在自检步骤上。**

> ⚠ 诚实说明：CI 日志接口返回 **403**（需 token），本机无 `gh` CLI，
> 因此**未能直接读取那一步的原始报错文本**。上述结论基于
> ①失败步骤的完整定义 ②同文件内已修正步骤的对照注释 ③本机机制复现。
> 建议修复后以绿灯作为最终确认。

### 问题 C-3：CI 只测「系统 Python」，未测产品真实形态
当前 CI 用 runner 自带 Python + pip 安装依赖。而 USB-WIKI 的卖点是
**Windows 自包含 Runtime**（embedded python + 预置依赖）。
`setup_runtime_windows.py` 构建出的运行时**从未在 CI 中验证过**。

## 七、数据安全

### 问题 W-1：用户 Markdown **未采用原子写**（P0 数据风险）

实测所有写文件位置：

| 位置 | 写什么 | 是否原子 |
| :--- | :--- | :--- |
| `crawler.py:401` | **`data/notes/*.md`（用户笔记）** | ❌ 直接 `write_text` |
| `crawler.py:415` | 快照 | ❌ |
| `crawler.py:594` | 原件 | ❌ |
| `crawler.py:745` | **导入转换结果（`.md`）** | ❌ |
| `archiver.py:233` | 资源池 | ❌（可重建，风险低） |
| `archiver.py:437` | CSS 资源 | ❌（可重建） |
| `config.py:119/203` | config.ini | ❌ |
| `embedder.py:124` | 探针缓存 | ❌（可重建） |

**数据库可以重建，Markdown 不可以。** 当前 `open → truncate → write` 模式下，
进程意外终止会留下半截笔记。

### 问题 W-2：外部编辑器并发修改无保护
indexer 读取文件时没有「读前 stat → 读后 stat 比对」逻辑，
用户在 Obsidian/Typora 保存的瞬间可能把半写入内容建进索引。

## 八、安全面

| 项 | 现状 | 判定 |
| :--- | :--- | :--- |
| 默认 Host 绑定 | `127.0.0.1`（`launcher.py:144` 可由 `--host` 覆盖） | ⚠ 无 `--allow-lan` 显式闸门与警告 |

| 请求体上限 | `MAX_BODY = 4MB` ✅ | ✅ |
| 原件留存上限 | `MAX_ORIGINAL_BYTES = 50MB` ✅ | ✅ |
| ZIP 炸弹防护 | `_zip_read()` 存在，**未见** entry 数量 / 解压后总尺寸 / 单 entry / 压缩比 限制 | ❌ 缺口 |
| 路径穿越防护 | 有 4 处 `relative_to` 校验 | ⚠ 需逐路由核实覆盖面 |
| API Key 泄露面 | 待逐项核实（日志 / `/api/status` / 异常回显） | ⚠ 待查 |
| URL 重复抓取 | **无任何 normaliz/source_url 去重** | ❌ 缺口 |

### 问题 SEC-1：抓取接口接受任意 URL 且无 SSRF 闸门
公开发布后，恶意网页可诱导本机请求 `127.0.0.1` / 内网 / 云 metadata 地址。

### 问题 SEC-2：同一 URL 可被重复抓取成多条笔记
已实证：同一篇 Grok 文章被保存两次，直接污染检索、关键词、主题分组与统计。
